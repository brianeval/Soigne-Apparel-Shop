How the Soigné shop works

A file-by-file guide to the customer storefront, account and order journey, admin portal, and how information moves between the browser, PHP, session, and MySQL.

How to read this guide: The PHP files are server-rendered pages. The browser requests a URL, PHP reads URL parameters, form data, session values and/or database rows, then returns HTML or a redirect. File paths below are relative to the project root. Use the Queries button for SQL and table relationships.

1. System overview

This is a PHP and MySQL apparel shop. Apache serves the project; PHP runs each requested .php file; MySQL stores accounts, products, cart rows, orders, stock, reviews and payment requests. The rendered HTML is sent back to the browser. The browser submits forms back to PHP using GET (URL parameters) or POST (form fields/files).

  1. Request: A customer opens a URL such as index.php, product.php?id=12, or cart/cart.php. The query-string value id=12 is available to PHP in $_GET.
  2. Bootstrap/shared setup: A page starts/resumes a PHP session and loads includes/config.php directly or through a shared include. Config opens the soigne_apparel database connection as $conn, sets UTF-8, and defines BASE_URL, APP_ROOT, and peso().
  3. Identity and input: The page reads $_SESSION, $_GET, $_POST, or $_FILES. Customer pages use includes/customer_auth.php when an active customer/VIP account is required. Admin pages use admin/includes/bootstrap.php.
  4. Data work: PHP executes SQL using MySQLi. Most form values go through prepared statements and bound parameters. Related writes such as checkout, cancellation, restocking and status changes use database transactions so the operation commits together or rolls back.
  5. Response: PHP renders HTML, outputs a PDF/image, or sends a redirect with header('Location: ...'). Flash notices and multi-step checkout state are kept in the session and shown on the next request.

Important A session carries the signed-in user ID, role, and short-lived workflow data between page requests; the database remains the source of truth for account status, VIP expiry, saved records, and current stock.

2. Customer journey: start to finish

  1. Enter the storefront. index.php reads products and their first color for the home listing. It uses includes/header.php for navigation/account/cart badge and includes/footer.php for the shared footer and image viewer. The cart badge is queried for the signed-in customer.
  2. Find products. Navigation points to department.php?dept=men|women|kids. Category links use category.php?category=.... brands.php displays brands or filters products by brand ID/name. The shared search.php?q=... search finds product/category names and brand names. These pages pass their result arrays to includes/product_grid.php; that helper loads color image paths through includes/product_images.php and formats VIP prices through includes/customer_auth.php.
  3. Inspect an item. A product card links to product.php?id=PRODUCT_ID. This page loads the product/category, colors, images and size variants (including stock), then renders its selectable product form and published reviews. The selected color/variant is sent to the cart handler. When cart_id is supplied, the page first confirms that cart row belongs to the signed-in user and matches this product, then displays the edit-cart form. product_view.php is a separate simpler all-products listing. size_guide.php and includes/product_size_guide.php provide sizing guidance.
  4. Sign in or register when needed. users/login.php accepts a username or email plus password, verifies the password hash and active account, refreshes the session ID, and stores the user ID/role/username in the session. It can return the customer to a safe requested page. users/register.php validates details, hashes the password, creates a users record and linked customers record in a transaction, and optionally saves a profile image via includes/profile_image.php. users/logout.php clears the login session.
  5. Add/change the cart. Product forms POST variant_id and quantity to cart/cart_add.php. It verifies the active account, verifies the variant and available stock, then inserts or increments the unique user/variant cart row without exceeding stock. cart/cart.php lists the current user's cart, computes totals and 10% VIP discount, and supports item removal, selected-item checkout, and links back to a product to change size/quantity. cart/cart_update.php validates ownership, product/variant compatibility and stock; if the target variant already has a cart row, it merges quantities. These actions redirect back and use session flash messages.
  6. Place the order. The cart's selected IDs are ownership-checked and stored in $_SESSION['checkout_cart_ids'], then the browser goes to orders/checkout.php. Checkout checks the CSRF token and shipping details, locks the selected cart/product rows, verifies stock, creates the order and order-item snapshots, applies VIP discount, reduces stock, and removes only those cart rows in one transaction. It then tries to send the confirmation email and redirects back to the checkout page to show the order number.
  7. Track or change an order. orders/orders.php lists only this customer's orders and their saved line details. While an order is pending, the customer can cancel it (which returns stock) or request valid size/quantity changes (the transaction restores old stock and reserves the replacement stock). Its tabs group pending, shipped, delivered, failed-delivery, paid/review, and cancelled orders. Only permitted order items from paid orders can be reviewed.
  8. Review a purchase. Forms in orders/orders.php POST to reviews/review_action.php. The handler checks session CSRF, order/user/item ownership and paid status, validates rating/text and stores or updates the customer's review. Reviews are displayed on product.php when published. admin/manage-reviews/index.php lets staff remove a review from public display.
  9. Maintain the account or Premium membership. users/profile.php loads and updates the signed-in customer's account/contact details and profile image. users/premium_checkout.php accepts a GCash receipt image, stores it outside the public web root, and creates a pending payment request. An administrator reviews it in the Premium Payments module; approval changes the customer's role to VIP and sets/extends the expiry. VIP receives the 10% product discount while active; includes/customer_auth.php synchronizes expiry/status back from the database.

3. Customer-side files and their responsibilities

Storefront and catalog

index.php home page; department.php department filter; category.php category filter; brands.php brand index/details; search.php search results; product_view.php simple product listing; product.php full product details, variants, cart form and reviews; size_guide.php size information.

Cart and ordering

cart/cart_add.php adds a size/quantity; cart/cart.php lists and removes/chooses items; cart/cart_update.php changes cart size/quantity; orders/checkout.php places an order; orders/orders.php lists and manages customer orders.

Accounts and reviews

users/login.php, users/register.php, users/logout.php, users/profile.php, and users/premium_checkout.php manage customer access and profile/Premium submission. reviews/review_action.php processes customer review create/update/delete actions.

Shared customer helpers

includes/config.php database/constants; includes/header.php shared nav and cart count; includes/footer.php footer/image preview; includes/customer_auth.php active account/VIP sync/discount; includes/product_grid.php and includes/product_images.php catalog cards/images; includes/profile_image.php profile uploads; includes/product_size_guide.php sizing data; includes/order_email.php SMTP emails and PDF receipt building.

4. Admin journey: sign-in to store operation

  1. Admin opens the portal. admin/login.php starts the session, issues a login CSRF token, and checks that the username/email belongs to an active admin account. On success it verifies the password hash, regenerates the session ID, stores the account identity/role and redirects to the safe admin destination (normally admin/index.php).
  2. Every protected admin request is gated. Admin pages include admin/includes/bootstrap.php. It loads the site config and redirect helper using paths rooted at __DIR__, requires an admin session, and rechecks that the database account is active. It supplies CSRF, escaping, one-time flash and pagination helpers. If access fails, it sends the browser to the admin login page.
  3. Dashboard navigation. admin/index.php shows product/customer/order counts, paid sales and recent orders. admin/includes/header.php renders the management sidebar/top bar; admin/includes/footer.php closes the shared layout. The sidebar links to each module and the storefront.
  4. Work in a module. A module loads current rows to display its page. Forms submit POST fields (including an action name, record IDs, and usually a CSRF token) to that module; PHP validates/authorizes the operation, updates the database, stores a flash result and redirects or redisplays validation errors.
  5. Sign out. admin/logout.php ends the admin session. admin/storefront.php is the admin-facing route for returning to the storefront.

Admin pages are server-rendered PHP, not a separate API. The browser does not send database changes directly; it submits form fields to the PHP file, and that file decides which database operation is valid.

5. Admin modules, file by file

Overview / authentication

admin/login.php authenticates active staff; admin/logout.php ends the session; admin/index.php builds dashboard statistics and latest-order list. admin/includes/bootstrap.php protects all module pages and defines reusable security/UI helpers. admin/includes/header.php draws the admin navigation/layout; admin/includes/footer.php closes it. admin/storefront.php is the navigation route back to the shop.

Manage Products

admin/manage-products/index.php lists products and handles product creation, adding categories and brands, and product deletion. Creating a product validates its brand/category/department/price and accepts its colors, sizes and images. admin/manage-products/edit.php handles one product: update basic fields; add/update/delete colors; add/update/delete size variants and stock values; and upload images per color. Image validation/storage is shared through includes/product_images.php; common numeric/price validation is in includes/product_validation.php; size choices use includes/product_size_guide.php.

Manage Inventory

admin/manage-inventory/index.php filters product variants by department, brand, category, color, size or search term and records supplier restocks. A restock request validates each variant, quantity and unit cost, locks the supplier/variant rows, inserts a restock header plus lines, increases stock, and commits atomically. admin/manage-inventory/view.php?id=... loads one restock and displays its received variant lines and totals.

Manage Orders

admin/manage-orders/index.php lists orders, lets admins create an order for an active customer, and allows deletion only for eligible unpaid orders. admin/manage-orders/edit.php?id=... shows one order, allows a shipping address change only while pending, and enforces state transitions: pending → shipped → delivered → paid, with cancellation or failed delivery returning reserved stock. It emails status changes through includes/order_email.php. admin/manage-orders/receipt.php?id=... serves a PDF only after an order is both delivered and paid.

Manage Reviews

admin/manage-reviews/index.php displays active/published customer feedback, prioritizes pending reviews if present, paginates results, and handles a CSRF-protected delete action. Deleted reviews are marked as deleted rather than physically removed.

Manage Customers / Premium

admin/manage-customers/index.php creates customer accounts, toggles active/inactive status, and prevents deleting customers with order history. admin/manage-customers/edit.php?id=... edits login/contact details and customer/VIP role, with optional password change or VIP renewal. admin/manage-customers/premium-payments.php lists submitted receipt requests and approves/rejects pending payments; approval extends VIP for one month in the same transaction. admin/manage-customers/premium-receipt.php?id=... validates and streams a receipt stored privately.

Admin changes are protected by the shared admin session gate; mutating forms use the session CSRF token. Pages use prepared SQL, validate IDs and statuses, and use transactions/row locks for changes that affect multiple records or stock.

2. How values reach a query

  1. A URL value such as ?id=12 is read from $_GET['id']; submitted fields are read from $_POST; uploads come through $_FILES; the logged-in user ID comes from the PHP session.
  2. PHP validates/converts input (for example integer IDs, allowed roles, statuses, lengths and numeric price ranges).
  3. For a parameterized query, PHP prepares a statement with ? placeholders, binds values with mysqli_stmt_bind_param(), and executes it. User-provided values stay separate from SQL syntax.
  4. SELECT results are read via mysqli_fetch_assoc() or mysqli_fetch_all(); the returned rows become PHP arrays used to build the page.
  5. For multi-record changes, mysqli_begin_transaction(), row locks such as FOR UPDATE, checks, and mysqli_commit()/mysqli_rollback() keep related updates consistent.
// Common pattern in the PHP pages
$stmt = mysqli_prepare($conn, 'SELECT ... WHERE id = ?');
mysqli_stmt_bind_param($stmt, 'i', $id);
mysqli_stmt_execute($stmt);
$row = mysqli_fetch_assoc(mysqli_stmt_get_result($stmt));

Binding type codes commonly used are i for integer, s for string, and d for floating-point numeric values; multiple values use a type string such as 'isi'. Some pages construct an IN (...) list only after validating IDs, or construct placeholder counts dynamically.

3. Customer-side query map

Catalog reads

index.php, department.php, category.php, brands.php and search.php select products or brands, join optional category/brand data, and select the first color for product cards. includes/product_images.php finds image paths; includes/product_grid.php renders results. product.php reads one product, colors/images/variants and published reviews. Search terms are passed to prepared statements.

Login, profile and VIP

users/login.php looks up an active customer/VIP by username or email, verifies its password hash, and downgrades expired VIP. users/register.php checks duplicate usernames/emails, then transactionally inserts account and profile rows. users/profile.php reads/updates account details. includes/customer_auth.php re-reads role/status/expiry to sync the session.

Cart and stock

cart/cart_add.php reads variant stock, then inserts/increments a cart row capped at stock. cart/cart.php joins cart → variant → color → product and scopes changes to the current user. cart/cart_update.php locks the owned cart item and target variant, checks product match and stock, then updates or merges duplicate lines.

Checkout

orders/checkout.php reads/locks selected cart lines and product/variant data, confirms stock, inserts the order and each order item (including sale price), reduces stock and removes purchased cart lines in one transaction. After commit, includes/order_email.php sends confirmation; email failure does not undo the order.

Orders and customer reviews

orders/orders.php selects orders scoped to user_id and uses order_transaction_details for totals/line details. POST actions lock and verify a pending order before stock or line changes. reviews/review_action.php verifies ownership of the paid order item before changing a review. product.php selects only published reviews.

Premium purchase request

users/premium_checkout.php checks for a pending payment, validates and privately saves the receipt, locks the active account and pending-request state, then inserts a premium_payments row. The file is outside MySQL; filename and MIME type are stored in the row.

4. Admin-side query map

Admin gate and dashboard

admin/includes/bootstrap.php checks the session and database admin status. admin/index.php aggregates product/order/customer counts, pending unpaid orders and paid sales; a second SELECT joins recent orders to order lines for the latest six rows.

Products

admin/manage-products/index.php reads categories/brands/products and writes catalog records. admin/manage-products/edit.php reads/changes product, color, image and variant records. Create/update/delete actions are validated and constrained by product/color/variant ownership. Image files are stored separately and their paths go into product_color_images.

Inventory

admin/manage-inventory/index.php reads suppliers, categories, variants and filtered stock. A restock locks supplier and variants, checks supplier ownership, creates restock header/lines and increments stock in one transaction. admin/manage-inventory/view.php joins restock lines to product/category/color/size.

Orders

admin/manage-orders/index.php joins order/customer data and the transaction view; order creation locks/validates customer and variants, writes order lines and decrements stock transactionally. Deletion checks allowed statuses and may restore stock. admin/manage-orders/edit.php locks the order before status changes and returns stock on cancellation/failed delivery. admin/manage-orders/receipt.php selects details only for delivered, paid orders.

Customers and Premium payments

admin/manage-customers/index.php lists/creates accounts, changes status, or deletes only accounts without order history. admin/manage-customers/edit.php updates account/profile, optionally password and VIP expiry. admin/manage-customers/premium-payments.php locks the pending payment; approval updates VIP role/expiry and payment review status together. admin/manage-customers/premium-receipt.php streams a validated private image.

Reviews

admin/manage-reviews/index.php counts and paginates active reviews, joins product and username, and soft-deletes by setting review status to deleted.

5. SQL views and snapshots

  • order_transaction_details is defined in the full schema and sql_files/replace_order_totals_with_transaction_details.sql. It joins order/item data to product/color/size names and calculates line/order totals. It exposes owner ID, not customer name; pages join users/customers separately when needed.
  • orders.shipping_address is the checkout-time address snapshot. order_items.price is the unit price recorded at sale time.
  • product_variants.stock is current stock. Checkout/admin order creation subtract it; cancellation/failed delivery restore it; restocks add received quantity.
  • VIP role/expiry are stored on users; auth synchronization or login downgrades an expired VIP.

6. Where to inspect SQL

  • sql_files/soigne_apparel_(updated).sql creates the schema/views and sample data. It drops and recreates tables; do not run it against data you need to keep.
  • Other files in sql_files/ are incremental changes/imports for reviews, payments, images, orders, VIP, customer status, categories, sizes and product data.
  • PHP pages execute queries at runtime rather than loading query files. Trace an operation from its $_GET/$_POST/session values through validation, mysqli_prepare(), parameter binding, execution and rendering/redirect.

function require_active_customer(mysqli $conn, string $redirect_path): void
{
    $customer_role = sync_customer_session($conn);
    if (in_array($customer_role, ['customer', 'vip'], true)) {
        return;
    }
    header('Location: ' . BASE_URL . 'users/login.php?redirect=' . urlencode($redirect_path));
    exit;
}
